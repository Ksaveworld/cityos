# 接口契约

> 模块之间只通过这些契约交互。任何模块内部怎么实现都不影响别人。
> **改这个文件前先说一声**——它是所有模块的共同依赖。

这份契约回答了周芷涵在 8/14 会上提的六个问题（见文末对照）。

## 1. Signal — 接进来的原始信号

```typescript
type SignalSource = '119接警' | '110接警' | '物业上报' | '烟感' | '市民上报'

/** 事实的可信度分级 —— 整套设计的良心所在，不要省略 */
type Confidence =
  | 'confirmed'   // 已被权威来源确认（如消防到场确认）
  | 'reported'    // 有人这么说（报警人口述）
  | 'inferred'    // 系统推断（如根据多条报警推断楼层）

interface Signal {
  id: string
  source: SignalSource
  rawAddress: string          // 原始地址文本
  timestamp: number           // Unix 秒
  text: string                // 原始描述，脱敏后
  reportedFloor?: number
  confidence: Confidence
}
```

**为什么要有 `confidence`**：高层火情的现场信息是混杂的——浓烟、有人被困、几楼着火，不同报警人说法不一，可靠程度不同。把"有人说"和"已确认"混为一谈，是这类系统最容易犯也最致命的错。

## 2. FireEvent — 事件容器

```typescript
type EventStatus = 'suspected' | 'confirmed' | 'closed'

interface Fact {
  key: string                 // 如 'floor' | 'trapped_people' | 'smoke_direction'
  value: string | number
  confidence: Confidence
  sourceSignalIds: string[]   // 溯源
}

interface FireEvent {
  id: string
  status: EventStatus
  buildingId: string          // 标准化建筑 ID
  location: [number, number]  // [lng, lat]
  signals: Signal[]           // 这个事件由哪些信号构成
  confirmedFacts: Fact[]      // 已确认
  pendingFacts: Fact[]        // 待核实 —— UI 上要单独展示
  createdAt: number
  updatedAt: number
}
```

### 事件融合规则（可解释，不用黑盒聚类）

新 Signal 进来时：

1. **地址解析** → 标准化建筑 ID + 坐标
2. **候选检索** → 查同建筑 ID 下未关闭的 FireEvent；再查坐标一定半径内未关闭的 FireEvent
3. **关联评分**（各项加权，全部可解释）：
   - 建筑 ID 一致
   - 坐标距离
   - 时间差
   - 语义指向（烟/明火/被困）
   - 独立来源类型（不同来源互证权重更高）
   - 关键楼层一致
4. **建立或更新**：
   - 无匹配 → 新建 `suspected` 事件
   - 高分匹配 → 关联进已有事件并刷新

> 时间窗和距离阈值是 **demo 配置项**，不声称是消防业务标准。这一点在文案里要写清楚。

## 3. Plan — 响应方案

```typescript
interface PlanMetrics {
  etaSeconds: number
  /** 误差带。两个方案差值落在误差带内时，系统应明说"无显著差异" */
  etaRange: [number, number]
  /** 执行这个方案后，其他区域出现的覆盖缺口 */
  coverageGapAfter: GeoJSON.FeatureCollection
  constraintsViolated: string[]
  /** 是否使用了降级算法（如 Valhalla 不可用时的直线估算） */
  degraded: boolean
}

interface Plan {
  id: string
  eventId: string
  label: string               // 'A' | 'B' | 'C'
  actions: Action[]
  metrics: PlanMetrics
  rationale: string           // 业务语言解释，不要出现算法术语
  requiresHumanApproval: boolean
}
```

**`etaRange` 不是可选项。** 方案 A 比 B 快 50 秒、而模型误差是 ±2 分钟——那个"对比"是噪声不是结论。敢说"这两个方案算不出区别"的系统，比永远给推荐的系统可信得多，这在评审现场是加分项。

## 4. Action — 动作

```typescript
type ActionType =
  | '派遣'        // 调派力量到现场
  | '预置待命'    // 移动到中间位置待命
  | '请求开路'    // 请交警在指定路口开路 —— 跨 119/110 系统
  | '通知物业'
  | '通知医疗'

interface Action {
  type: ActionType
  target: string              // 资源 ID 或部门
  detail?: string
  /** 哪些动作必须人工批准 —— 芷涵问的第六条 */
  approvalLevel: 'auto' | 'human'
}
```

### 审批级别的分配原则

| 动作 | 级别 | 理由 |
|---|---|---|
| 预置待命 | `auto` | 不消耗力量，可撤回 |
| 通知物业 / 通知医疗 | `auto` | 信息类，无处置权变更 |
| **派遣** | `human` | 消耗力量，影响其他区域覆盖 |
| **请求开路** | `human` | 跨部门，涉及交警指挥权 |

**原则：凡是会改变其他区域资源状态、或跨越部门权限边界的动作，一律 `human`。**

## 5. 「请求开路」为什么单列

这条来自 8/14 长春基层消防的一线调研：

> 消防车属于紧急车辆，实际行驶逻辑和普通车辆不同，但普通导航仍按普通车辆规则规划。消防员只能自己判断怎么最快到达，判断不一定准确。即使通知了 110，两边系统信息不流通，**不知道调度哪些给开路**。

这是一线自己提出的、未被满足的需求，而且：

- 本质是**跨部门协同断裂**（119 知道去哪、110 有交警，两边系统不通）
- 是**空间与路径计算**问题，正是我们能算的
- 天然是**多方案对比**的形态：几条路线各自 ETA、哪几个路口值得开路、开路后各省多少秒
- **不依赖历史方案库和 RAG**，绕开了落地最难的一环

**这是火情场景里推演含量最高的一块，优先做。**

## 7. 医疗接收资源异常 P0

本节冻结第一条正式后端纵向链路：**原接收医院被权威来源标记为临时不可接收 → 原方案与批准失效 → 生成替代方案预览 → 人工确认 → 模拟任务下发 → 回执与审计**。

P0 只处理明确收到的“临时不可接收”事件。接口超时、来源断开或数据过期只能进入 `unknown`，不得推断医院不可接收。医院满载、永久关闭和跨区域转运留到后续版本。

### 7.1 运行模式

```typescript
type DataMode = 'demo' | 'live' | 'live-degraded'
```

| 模式 | 数据 | 写动作 |
|---|---|---|
| `demo` | 明示模拟事件与资源状态，携带数据集版本 | 只允许模拟执行 |
| `live` | 经授权接口进入的状态 | 按权限与人工确认执行 |
| `live-degraded` | 最后一次有效真实快照，必须显示更新时间 | 强制只读，禁止 confirm/execute |

任何模式切换都必须进入审计记录。`live` 接口失败时不得自动混入 demo fixtures。

### 7.2 来源与适配器事件

```typescript
interface EvidenceSource {
  sourceSystem: string
  externalEventId: string
  schemaVersion: string
  sourceSequence?: number
  occurredAt: number          // Unix 秒，来源声称的发生时间
  receivedAt: number          // Unix 秒，CityOS 接收时间
  confidence: Confidence
}

interface FacilityStatusChanged {
  eventId: string
  eventType: 'facility.status.changed'
  mode: DataMode
  incidentId: string
  facilityId: string
  status: 'available' | 'temporarily_unavailable' | 'unknown'
  reasonCode: 'source_reported_unavailable' | 'source_recovered' | 'unverified'
  aggregateVersion: number
  idempotencyKey: string
  source: EvidenceSource
}
```

去重作用域为 `sourceSystem + externalEventId`。相同事件重复提交必须返回第一次处理结果；较小的 `aggregateVersion` 或较旧的 `sourceSequence` 不得覆盖新状态，但必须记录为迟到事件。

### 7.3 医院与方案版本

```typescript
interface Facility {
  id: string
  name: string
  location: [number, number]
  status: 'available' | 'temporarily_unavailable' | 'unknown'
  statusVersion: number
  updatedAt: number
  source: EvidenceSource
}

type PlanVersionStatus = 'draft' | 'approved' | 'stale'

interface MedicalCandidate {
  facilityId: string
  routeId: string
  etaSeconds: number
  etaRange: [number, number]
  receivingStatus: Facility['status']
  riskDelta: number
  degraded: boolean
  sourceIds: string[]
}

interface PlanVersion {
  id: string
  incidentId: string
  version: number
  inputVersion: number
  inputSnapshotHash: string
  status: PlanVersionStatus
  candidates: MedicalCandidate[]
  approvedBy?: string
  approvedAt?: number
  createdAt: number
}
```

设施状态、路线输入或资源状态发生变化时，引用旧输入的 `approved` 方案必须立即转为 `stale`。批准永远绑定具体 `planVersion` 和 `inputSnapshotHash`，不得自动迁移到新版本。

### 7.4 Action Preview、确认与执行

```typescript
type ActionRunStatus =
  | 'previewed'
  | 'confirmed'
  | 'queued'
  | 'running'
  | 'succeeded'
  | 'failed'
  | 'unknown'
  | 'reconciling'
  | 'cancelled'
  | 'expired'

interface AdjustResourcesPreview {
  actionRunId: string
  actionType: 'adjust_resources'
  incidentId: string
  planVersion: number
  expectedIncidentVersion: number
  previewHash: string
  expiresAt: number
  riskLevel: 'high'
  requiresHumanApproval: true
  previousFacilityId: string
  candidateFacilityIds: string[]
  selectedFacilityId: string       // 人工选择，必须属于当前方案候选项
}

interface ConfirmActionRun {
  actorId: string
  idempotencyKey: string
  previewHash: string
  expectedPlanVersion: number
}

interface ExecuteActionRun {
  actorId: string
  idempotencyKey: string
  expectedStatus: 'confirmed'
}
```

不变量：

1. Preview 可以写审计记录，但不得修改正式业务状态。
2. 未确认、已过期或引用 stale 方案的 ActionRun 绝不能执行。
3. confirm 必须校验 `previewHash`、`expectedPlanVersion` 和当前输入版本。
4. execute 前再次校验 `expectedStatus` 和事件版本。
5. 同一操作者、动作类型和幂等作用域中的相同 `idempotencyKey` 必须返回同一个 ActionRun 或执行结果。
6. 外部请求可能成功但响应丢失时进入 `unknown → reconciling`，不得盲目重试。
7. Agent 只能读取、归并和解释；候选资格、数值计算、排序和状态迁移由确定性代码负责。
8. Preview 必须绑定 `selectedFacilityId`；confirm 只确认该具体选择，不得在 execute 阶段自动换成其他候选项。

### 7.5 任务包与回执

```typescript
type TaskFeedbackStatus =
  | 'accepted'
  | 'en_route'
  | 'arrived'
  | 'completed'
  | 'exception'
  | 'unknown'

interface TaskPackage {
  id: string
  incidentId: string
  planVersion: number
  version: number
  mode: DataMode
  simulated: boolean
  actionRunId: string
  facilityId: string
  status: 'issued' | TaskFeedbackStatus
  createdAt: number
}

interface ExecutionFeedback {
  id: string
  taskPackageId: string
  externalFeedbackId: string
  status: TaskFeedbackStatus
  occurredAt: number
  receivedAt: number
  detail?: string
}
```

同一 `externalFeedbackId` 只能生效一次。异常反馈不得直接触发重新下发；必须生成新方案版本并重新进入 preview/confirm。

### 7.6 HTTP 合同

```text
GET  /v1/incidents/{id}

POST /v1/action-runs/{id}/execute

```

所有写请求必须提供：

- `Idempotency-Key`
- `X-Actor-Id`
- `X-Data-Mode`
- 输入版本或预期当前状态

统一错误结构：

```typescript
interface ApiError {
  error: {
    code: string
    message: string
    traceId: string
    retryable: boolean
    currentVersion?: number
  }
}
```

后端不可用时，前端必须进入显式降级状态；不得伪造成功响应或静默读取 demo fixtures。
