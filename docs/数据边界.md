# 数据边界

> 哪些数据是真的、哪些是模拟的、依据是什么。
> **写任何涉及"我们用了真实数据"的文案前，必读本文。**
>
> 「真实与诚信」是比赛的正式评分维度，官网原话：**呈现的东西，必须是真的。**

---

## 总原则

**真实城市骨架 + 明示模拟资源。**

宁可标明是模拟，也绝不让人产生"我们接入了政府真实数据"的错觉。

对外可以说的：
> 城市底图、路网、医院与派出所位置是真实公开数据；消防能力、资源实时状态、事件流是模拟数据，界面上有标注。

对外**不能**说的：
> ~~我们接入了消防物联信号~~ / ~~我们对接了 119 接警系统~~

正确的表述是：**我们设计了对接能力和数据结构，Demo 阶段按公开规范造模拟数据——字段和结构是真的，数据是模拟的。**

## 实测数据（2026-08-14，OSM Overpass API）

### 建筑属性

| 区域 | 建筑总数 | 有层数标注 | 覆盖率 |
|---|---|---|---|
| **深圳**（福田罗湖，22.50–22.56N / 113.90–114.00E，约 68km²） | 6,357 | 3,064 | **48.2%** |
| **南京**（河西，32.00–32.06N / 118.70–118.80E，约 63km²） | 9,271 | 942 | **10.2%** |

建成年代（`start_date`）：深圳 **35 栋（0.55%）**，南京 **8 栋（0.09%）**。都等于没有。

深圳同区域另有 `height` 标注 **336 栋（5.29%）**，可作层数缺失时的补充，但覆盖同样太低。

**结论：建筑轮廓可以用真实数据；层数视城市而定；年代基本拿不到。**

### POI

**注意口径**——下表深圳是**全市**，南京是**主城区**，两列不可直接比较。

| 类型 | 深圳全市 | 南京主城区 |
|---|---|---|
| 消防站 | 98 | 19 |
| 医院 | 167 | 114 |
| 派出所/警局 | 216 | 83 |
| 消火栓 | — | **8**（实际为万级，等于没有）|
| 避难集合点 | — | **0** |

同 bbox（福田罗湖 68.7km²）内实测：消防站 **5**、医院 **10**、派出所 **12**、消火栓 **1**、避难场所 **0**。

消防站的 5 要小心用。按《城市消防站建设标准》建标 152-2017，设在城市的一级普通消防站辖区不宜大于 7km²，68.7km² 对应**至少 10 个站**。**OSM 覆盖约一半，必须按消防救援支队公开名录人工补点。**

## 道路属性实测（2026-08-16，OSM Overpass API）

这一节回答的是「消防车路径推演能不能用真实约束」。**结论是不能。**

标注率的分母统一为**可通行道路条数**（`highway` 取 motorway / trunk / primary / secondary / tertiary 及其 link 型，加 unclassified / residential / living_street / service，**排除 footway / cycleway / path / steps**）。

| 数据项 | 深圳福田罗湖（68.7km²） | 南京主城区（约 1,100km²） |
|---|---|---|
| 全部 highway way | 9,875 | 33,265 |
| **可通行道路** | **5,269** | **25,018** |
| 主干道 | 1,214 | 4,924 |
| 限高 `maxheight` | 21（**0.40%**） | 7（**0.03%**） |
| 限重 `maxweight` | **0** | 4（0.02%） |
| 限宽 `maxwidth` | **0** | **0** |
| 路宽 `width` | 7（0.13%） | 12（0.05%） |
| 车道数 `lanes` | 843（16.00%） | — |
| 单行道 `oneway=yes` | 2,578（**48.93%**） | 8,623（34.47%） |
| 转向限制关系 | 23 | 26 |
| 信号控制路口 | **513** | **208** |
| 公交专用道标注 | 15 | — |

### 三条必须记住的结论

1. **车辆尺寸硬约束（限高/限宽/限重）等于没有。** Valhalla 的 `truck` costing 支持 height / width / weight 参数，但深圳只有 21 条路会命中 `maxheight`，限重限宽是 0。**这一层整体标为模拟。**最小转弯半径 OSM 根本没有对应字段。

2. **特权规则三条里只有单行道逆行站得住。** Valhalla 有 `ignore_oneways` / `ignore_restrictions` / `ignore_access` / `ignore_closures`，传参就能开，不用改 costing 源码。但它们是**全局开关，没法按路段选择性豁免**。
   - 逆行豁免 → 2,578 条（48.93%），放开等于可行子图边数接近翻倍，**能演**
   - 禁左豁免 → 转向限制关系仅 23 条（0.44%），开与不开路径大概率一样，**演不出来**
   - 公交道借用 → 专用道标注仅 15 条，**演不出来**

   **做法**：同一组起终点跑两次（全开 / 全关），到场时间差就是特权收益的上下界，填进 `PlanMetrics.etaRange`。

3. **信号控制路口是深圳相对南京最大的优势。** 深圳每百条可通行道路对应 9.7 个信号灯路口，南京只有 0.83 个，**相差 11.7 倍**。「关键路口判定」第一条判据（信号控制路口，无灯路口不下发）在深圳有数据，在南京没有。

> 产品侧方案里的「路网 OSM 实测 33232 条」是**南京全部 highway way**。消防车可通行子集是 25,018 条，比那个数少 33%。对外报规模用后者。

## 逐项判定

| 数据 | 真 / 模拟 | 来源与说明 |
|---|---|---|
| 城市底图 | **真** | OpenFreeMap 矢量瓦片，免费无 key |
| 路网 | **真** | OSM，ODbL 许可，可落库（需署名 + 同源共享） |
| 医院、派出所位置 | **真** | OSM |
| 消防站位置 | **真（需补点）** | OSM 覆盖不全，从消防救援支队公开名录补，人工标点 |
| 建筑轮廓 | **真** | OSM |
| 建筑层数 | **部分真** | 视城市，缺失部分按用途给默认值并标注为估算 |
| 建筑年代 | **模拟** | 公开渠道基本没有（深圳 0.55%，南京 0.09%）|
| 信号控制路口 | **真** | OSM `highway=traffic_signals`，深圳福田罗湖 513 个 |
| 单行道分布 | **真** | OSM `oneway=yes`，深圳福田罗湖 2,578 条 |
| 转向限制 | **真但太稀** | 深圳福田罗湖仅 23 条，禁左豁免演不出差异 |
| **道路限高/限宽/限重** | **模拟** | 实测标注率 0.40% / 0% / 0%，见「道路属性实测」|
| **最小转弯半径** | **无字段** | OSM 没有对应 tag，从硬约束清单里去掉 |
| 消防车规格参数 | **真** | 厂商公开产品参数 |
| 路口信号配时、常态拥堵程度 | **模拟** | 无公开来源 |
| **消防站能力**（车辆数、车型） | **模拟** | 任何公开渠道都拿不到 |
| **医院急救床位** | **模拟** | 同上 |
| 消火栓 | **模拟** | 按规范密度（间距约 120m）生成分布 |
| 避难场所 | **模拟** | 公开数据没有 |
| 资源实时状态 | **模拟** | 在消防、卫健内部系统 |
| 事件流（警单） | **模拟** | 119/110 接警数据涉密，按公开的接处警规范造格式 |
| 消防设施物联状态 | **模拟** | 在消防救援机构手里，第三方拿不到 |

### 广州演示资源 POI 口径（2026-08-20 补充）

- 基础资源快照：`public/data/liwan_resources.geojson`，由 OSM / Overpass API 于 2026-08-14 获取；当前包含广州演示范围内的医院、消防站和派出所公开静态点位。
- UI 只把公开快照中的名称、类型与经纬度标为“公开静态 POI”。结构化地址缺失时显示“公开快照未提供”，不自行补全。
- 多宝消防救援站与广州市红十字会医院于 2026-08-20 通过 OSM Nominatim 反查复核，分别保留 [OSM way 1079152727](https://www.openstreetmap.org/way/1079152727) 与 [OSM way 598391042](https://www.openstreetmap.org/way/598391042) 链接；其余点位回溯到本地快照与 [OSM 版权/ODbL 页面](https://www.openstreetmap.org/copyright)。
- “在途 / 待命 / 现场”、人员、车辆、能力、ETA、占用事件和调派关系全部是模拟运营数据。即使一张资源卡映射到真实设施名称和坐标，也不代表该设施真实参与事件或具备界面所示能力。
- 道路仍是公开底图/路网背景。城市总览、今日事件和资源调度中的普通道路点击不承载业务信息；仅处置链显式封路步骤可选择 OSM way 并触发本地模拟重算。

## 两个重要限制

### 高德/百度 POI 不能落库

商业地图 API 的服务条款限制数据持久化存储，只能在线调用。而且它们同样不提供建筑层数和年代。

**结论：整条链路绕开商业地图 API，全部用 OSM + 人工补点。**这样既无合规风险，又能落库。

### 建筑内部结构完全没有

火灾蔓延的物理仿真需要建筑内部结构、材料、通风、荷载。这些一样都没有。

**所以不能声称"推演火势蔓延"。** 我们推演的是**资源与覆盖的未来状态**，不是事件本身的物理演化。

## 摄像头能力现状（2026-08-14 调研）

用于支撑「不做感知层」这个决策：

- **人像卡口是专用硬件**（非球面镜片、宽光谱透射、前端特征提取），普通球机做不了人脸识别——不是没开功能，是硬件不支持
- 雪亮工程的部署原则是「普通监控广覆盖、智能卡口重点布控」。某县级案例：视频监控总计约 1,353 路，其中普通监控 976 路（72%），**人像卡口仅 75 路（约 5.5%）**
- **热成像在街面几乎零部署**，只在森林防火、化工园区、物流仓库、古建筑、变电站、危废仓库这类特定高风险场所
- **但可见光烟火识别是成熟商用方案**，可直接叠加在存量摄像头上，供应商众多

**结论：街面火情检测不是技术空白，是红海。我们不做。**

## 一线流程验证（2026-08-14，长春基层消防访谈）

用于支撑产品定位：

- 消防站电脑自动弹出警单，含报警人、电话、地址、警情
- **出警路上消防员自己用高德导航，并打电话给报警人确认信息**
- **导航按普通车辆规则规划，消防车实际通行逻辑不同**
- **即使通知 110，两边系统不通，不知道该调度哪些路口开路**
- 现场照片视频先发工作微信群，再由人上传录警系统，中间大量人工
- 排班调度智能化程度低，靠人工打电话
- 无人机已配备，出警前先飞查看，**但拍到的信息未自动进入调度流程**

**这几条是产品价值锚点的一手依据，可以引用。**
