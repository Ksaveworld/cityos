## 二、上下文补齐快速通道

纪要原话：点击事件处理后直接生成 AI Brief 快照，汇总已知确定信息后直接跳转至方案展示，替代逐环节点击操作。

会上白板（wiki「用户路径」那张手写图）写的是：Signal ✓ → Event ✓ → Context ✓ → AI Brief，**AI Brief 会总结全部的上述信息**，下面一个「查看卡面」按钮 ⇒ 流程连通。

### 现状

`RightPanel.tsx` 的 `openDetail(item, step)` 进来落在 `step = 0`（Signal），用户要点四次「查看下一环」才到方案。`foundationCollapsed` 只是把轨道上的四行折起来，内容面板还是逐环翻。

### 改法

1. 事件卡「进入处置」→ `openDetail(item, 3)`，直接落到 AI Brief。
2. AI Brief 面板改成**快照汇总视图**：把 Signal 的三条输入、Event 的已确认/待核实、Context 的补齐项压成一屏摘要，而不是只显示 `informationGaps`。已有数据都在 `scenario.event` 里，不用新增 engine 逻辑。
3. 快照底部一个主按钮「查看方案」→ `onStepChange(4)`。
4. 想逐环看的路径保留：轨道上「事件研判」展开后仍可点进 1/2/3/4 单环。

**验收**：从首页事件卡点「进入处置」，两次点击之内看到方案对比；逐环查看仍然可达。

`LiwanStepPanel` 的 `step === 5` 分支删掉。**`activeStep` 下标不要重排**——engine 的 `ChainStep` 九环不动，下标语义就别动，`step === 5` 直接落回 `StrategyPanel` 即可，改动面最小。

### 不能丢的边界

纪要只说取消**独立环节**，没说取消人工确认。CLAUDE.md 的差异化叙事是「由人工确认后生成协同任务」，这是产品红线。

## 五、事件面板支持拖拽调宽

纪要原话：支持用户拖拽左侧事件面板边缘调整宽度，解决当前面板偏窄、内容展示空间不足的问题。

### 根因是固定 px，不是数值不够大

`App.tsx:249–254`：

```
detailMode  → 'grid-cols-[minmax(0,1fr)_520px]'
incidents   → 'grid-cols-[minmax(0,1fr)_420px]'
overview    → 'grid-cols-[190px_minmax(0,1fr)_320px]'
```

520px 在 1440 视口下是 36%，看着正常；会上截图是 2315 CSS px 的宽屏，同一个 520px 只剩 22%——**越宽越小**。这就是「面板偏窄」的来源。

### 改法

两步都要做：

1. **默认值改成比例带下限**，先解决宽屏缩水：
   `detailMode → 'grid-cols-[minmax(0,1fr)_minmax(440px,33%)]'`
   `incidents → 'grid-cols-[minmax(0,1fr)_minmax(380px,28%)]'`
2. **加拖拽把手**：右栏左边缘一条 4px 命中区（视觉 1px），`pointerdown` 起拖，宽度存 state（`useRef` 存像素、拖动中直接改 `style.gridTemplateColumns`，**不要每帧 setState**——`App.tsx:77` 那条注释已经踩过这个坑，逐帧 setState 会让顶栏、左右栏、统计卡和整张地图跟着重渲染）。
   钳位 `[360px, 46%]`，`dblclick` 复位到默认比例。宽度落 `localStorage`，离线演示重开还在。

拖完要通知地图重算 padding，见第十四节。

`overview` 的 320px 同理缩水，但首页三栏地图是主体，**先不动**，等这条验收完单独评估。

**验收**：1440×900 与 2560×1440 两个视口下右栏都稳定在 1/3 附近；拖拽流畅无卡顿；`min-w-[1180px]` 下不出现横向滚动。

### 楼体：28 块独立楼板

不要用连续色带。第一版做成 7 段首尾相接（45-48、48-51、51-54…），
结果 19F 和 20F 糊成一坨、17F 和中性层分不开，楼层边界完全读不出来。

改成派生一份 GeoJSON：取该建筑多边形复制 28 份，每份带 `floor` 和 `state`，
建 source `routine-floors`，**一个** `fill-extrusion` 图层用表达式驱动。

```
base    ['+', ['*', ['-', ['get','floor'], 1], 3],
        ['match', ['get','state'], 'reported', 0.95, 0.35]]
height  ['-', ['*', ['get','floor'], 3],
        ['match', ['get','state'], 'reported', 0.95, 0.35]]
```

普通楼板 2.3m 厚、上下各留 0.35m 缝；**待核实层只有 1.1m 厚**。

| state | 楼层 | 颜色 |
|---|---|---|
| `plain` | 其余 | `rgba(174,183,197,0.88)` |
| `refuge` | 16F | `rgba(48,164,108,0.88)` |
| `fire` | 18F | `rgba(229,72,77,0.97)` |
| `smoke` | 19F | `rgba(232,150,74,0.82)` |
| `reported` | 20F | `rgba(199,120,22,0.45)` |

`fill-extrusion-vertical-gradient` 必须是 `false`。MapLibre 默认给挤出体加竖向渐变，
会把每块楼板的上下边缘糊掉，正好抵消留缝的效果。

**厚度差是形状编码，不是随手调的数。** 挤出体块画不了虚线描边，
「已确认与待核实必须用不同形状编码，不能只靠颜色」这条规则靠 1.1m vs 2.3m 守住。
不许把 reported 的 0.95 改回 0.35。

### 镜头：方位角是算出来的，不是试出来的

初版 `bearing = -24`，意味着镜头站在方位角 **156°**。而周边两栋高楼恰好都在 **157°**：

| 名称 | 距离 | 高 |
|---|---|---|
| 中庸·金寓 | 58m | 60m |
| 中国人民银行 | 97m | 78m |

色带在 45–60m 高度，等于隔着一堵 60m 的墙在看。

200m 内 22 栋建筑里有 4 栋高于 42m，方位角 157 / 157 / 206 / 327。
**环绕转满一圈必然会再撞上，光换初始角度不够。**

```
center    [113.253289, 23.113914]
zoom      17.6
pitch     62
bearing   -105          镜头方位角 75°，该扇区 200m 内最高只有 18m
duration  2200
```

环绕改成 **扇形往复**，在 `-135` 到 `-75` 之间来回摆（方位角 45°–105°），
每帧 0.05°，到端点反向。这样永远转不到那三个有高楼的方向上去。

### 周边楼减淡

距目标 200m 内的 22 栋（不含目标楼）单独一层 `routine-context-buildings`，
`fill-extrusion-opacity 0.22`，颜色 `#C9D0DA`。`buildings-3d` 的 filter 要同时排除
目标楼和这 22 栋，否则打架。

**只降透明度，不许压低这些楼的高度。** 把挡视线的楼改矮是最省事的做法，
但真实建筑高度是 OSM 公开数据，改矮就是失真，「真实与诚信」是正式评分维度。

### 动态的三条纪律

1. **不许走 React state。** `App.tsx:77` 的注释写了教训：逐帧 setState 会让顶栏、
   左右栏、统计卡和整张地图跟着重渲染。用 `useRef` + `rAF` + MapLibre 命令式 API，
   烟气只改 paint property，不触发重新布局。
2. **用户一操作就永久停。** 监听 `dragstart` / `zoomstart` / `rotatestart`，
   停了就不再自动接管。
3. **`document.hidden` 停 rAF，卸载 `cancelAnimationFrame`，切场景解绑事件。**
   另外尊重 `prefers-reduced-motion`，开启时两项动画都不启动。

纪要写的是「首阶段若工作量较大则暂不落地，仅做文字说明」，**8/19 会后已推翻，120 路线要做。**

评估下来工作量不大，数据和求解器都是现成的：

|---|---|

### 改法

`createRoutingRuntime()` 现在只吸附 `GUANGDA.location` 一个起点，加第二个：

```ts
// 按路网距离取最近医院，不是直线距离——直线最近的可能隔着珠江
const medical = nearestHospital(resources, site.center)
const medicalFrom = nearestNode(baseline, medical.location)
```

`buildRoutingView()` 里加第三次求解。**用 `baseline` 图不用 `privileged`**——救护车没有逆行特权，这是特权规则只给消防车的产品判断，别偷懒复用 A 的图。

```ts
const routeM = solve(runtime.baseline, runtime.medicalFromNode, runtime.toNode, { closedWayIds })
```

封路重算、`leaked` 完整性校验、不可达降级这三条逻辑对 120 一视同仁，照抄 A/B 的分支。

### 120 不是第三个候选方案

**别把它塞进 `plans` 数组。** A/B 是「二选一」的候选，120 是**和消防并行派发**的另一条线，两者语义完全不同。混进去会让「方案比较」这个核心叙事变浑。

单独一个 `medicalRoute` 字段，地图上单独一层，方案卡里不出现。

### 真正值钱的是这个

有了 120 路线，**推演能多输出两条结论**，这才是加它的理由，不是为了地图上多一根线：

1. **医疗到场 ETA vs 消防到场 ETA**——伤员转运窗口对不对得上
2. **120 路线和消防路线的共线段**——共线意味着相互干扰，封路重算时两条线可能一起失效

第二条尤其是「计算既定选项的后果」的正面例子：封一条路，界面同时告诉你消防绕了多远、救护车受没受影响。共线段判断复用 `buildRouteSegments()` 里已有的 `shared` 逻辑。

**验收**：地图上三条线可区分；封路后 120 路线跟着重算；方案卡里没有 120；ETA 对比里能看到医疗到场时刻。

## 十三、方案展示时聚焦方案路段

`CityMap.tsx:419` 的 `fitBounds`：

```js
padding: { top: 76, right: 168, bottom: 104, left: 104 },

```

`maxZoom: 14` 把整条 A/B 路线拉满全屏，wiki 说「不用扩大太多展示」。

## 十五、Commit 粒度

一个 commit 一件事。建议切成：

```
feat(components): 事件处置直达 AI Brief 快照与方案展示
refactor(components): 取消方案弹窗与独立拍板环，详情改行内展开
refactor(components): 处置九环对外改称处置环节并收口分组
feat(components): 事件面板支持拖拽调宽并改用比例默认值
feat(components): 火情高层改用地图楼体分层与镜头推进
docs(docs): 色板补入医疗路线 #0E9AA7
feat(engine): 新增 120 到场路线求解与共线段判断
fix(components): 日常响应模拟移到本地数据覆盖内的高层
refactor(components): 地图常驻浮层收敛为标题卡与图例
fix(components): 方案环聚焦当前方案路段并按右栏宽度重算 padding
feat(components): 首页事件卡按处置状态分档提示
```

每个提交前 `npm run typecheck` 必须通过，带 Codex 自己的 `Co-Authored-By` trailer。
