# CityOS Chatbot · MiniMax 服务端配置

两个前端助手统一调用同源接口 `GET/POST /api/chat`。浏览器不会直接请求 MiniMax，也不会读取模型密钥。

## 本地开发

在仓库根目录的 `.env.local` 中设置以下服务端变量，然后重新启动 `npm run dev`：

```dotenv
MINIMAX_API_KEY=在本机填写新密钥
MINIMAX_MODEL=MiniMax-M2.7
MINIMAX_BASE_URL=https://api.minimaxi.com/v1
```

不要给密钥变量添加 `VITE_` 前缀；Vite 会把这类变量暴露到浏览器包中。`.env.local` 已被 Git 忽略，不应提交。

## Vercel

在项目的 Environment Variables 中新增 `MINIMAX_API_KEY`，覆盖 Production、Preview 和 Development 中实际需要的环境。`MINIMAX_MODEL` 与 `MINIMAX_BASE_URL` 可选；未设置时使用上面的默认值。

也可以在已登录的终端中交互式执行：

```powershell
vercel env add MINIMAX_API_KEY
```

输入密钥时不要把值放在命令行参数、脚本、提交记录或聊天消息里。环境变量变更后需要重新部署。

## 当前业务边界

- MiniMax 已负责理解问题和生成结构化回复。
- 页面事实带稳定 `factId`；非推断依据的文字、可信等级与关联来源由服务端从页面上下文原样派生，模型不能自行改写。
- 建议动作名称和审批要求由服务端动作白名单派生；模型只能解释理由与影响，不能自行声明“已批准”或“已执行”。
- 知识副驾目前只使用页面中的演示条目；未接生产知识库、RAG、检索权限或正式入库工作流。
- 知识条目的来源是条目级关联范围，不代表每个字段都已由每个来源逐一核实。
- 调度副驾目前只使用事件级模拟 Ticket；未接稳定 `taskId`、真实资源状态、逐任务回执或真实调度写接口。
- 模型不能直接调派、批准、发送任务或写入正式知识库；写操作继续由确定性的业务界面和人工门禁承担。

## 公开上线前仍需补齐

- 当前同源校验和进程内限流只适合演示环境；公开 C 端上线前，需要接入真实用户身份、租户隔离、分布式限流和预算告警。
- 需要由业务与安全负责人确认哪些调度、警情和医疗字段允许发送给第三方模型，以及日志、留存和删除策略。
- `GET /api/chat` 的“已配置”只表示服务端存在密钥，不等于 MiniMax、生产知识库或真实调度系统已经健康；成功问答才证明本次模型调用可用。

## 当前验收状态

- 已验证：未配置密钥时明确失败且不回退本地伪答案；MiniMax 请求与回复结构、来源、动作、审批和错误码均有服务端校验。
- 已验证：浏览器使用结构化 mock 响应跑通两个助手的渲染、候选字段、旧快照提示和人工门禁。
- 尚未验证：使用有效新密钥完成一次真实 MiniMax 成功问答、真实延迟与实际账户额度；不能据此宣称生产可用。
