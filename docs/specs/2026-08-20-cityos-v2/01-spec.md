# CityOS v2 · Product Spec

> 状态：Gate 1 待确认。本文冻结“做什么、什么不能做、哪些状态不可绕过”；技术文件映射和并行 Owner 留到 `03-plan.md`、`04-tasks.md`。

## 目标

在现有 CityOS 演示的真实/模拟边界内，交付可离线演示的两条产品链：

```text
独立进入态 → 城市安全总览 → 日常响应 / 历史案例
```

日常响应证明：工作人员可通过两个模拟入口进入同一受控工作流，系统形成可解释的候选方案，经人工批准后形成模拟任务和送达状态。

历史案例呈现：5·16 的公开事实、未知项与 CityOS 模拟推演被严格分开，并通过独立动态舞台和三轨口径对比呈现模拟策略差异。

## 范围

### In

- 独立进入态；
- 119、110、120、交通、重大布防五个可演示功能场景；

- 任意自然语言事件解析、任意输入保证可用；

- 新建第二套路由、地图或业务引擎。

## 进入态与总览

### REQ-ENTRY-01 独立进入态

首页是同一应用内的进入态，不是第二套业务页面。必须展示：

- CityOS 名称；
- 一句话定位；
- 城市与更新时间；
- “真实城市骨架 + 明示模拟资源”的数据说明；
- 主按钮“进入城市安全总览”；
- “日常响应”“历史案例”两个快捷入口。

进入总览后才展示今日事件、待决策、执行异常、天气和道路等业务信息。

### REQ-BOARD-01 主看板四指标与今日事件中心

主看板四张指标卡不得只切换工作区后继续继承旧场景。指标数字与去向固定为：

- 今日事件：从统一 `TodayEvent` 台账计算 23 起，进入“今日全部”；
- 待人工决策：从同一台账计算 3 起，进入“待人工决策”；
- 执行异常：从同一台账计算 2 起，进入“执行异常”；
- 在途单位：从资源台账计算 17 组，进入资源调度并预筛“在途”。

顶部“事件处置”与前三张事件指标共用一个今日事件中心。事件列表、筛选、详细说明和城市事件点位保持同步；事件卡或地图点位第一次点击只能选择事件、展开详细说明并聚焦地图，不得直接进入处置链。只有五类样板事件提供显式“进入处置”，分别进入 119、110、120、交通和重大布防；普通台账事件显示“未配置处置链”。

今日事件列表态必须忽略此前活动的火情、重大布防等具体场景状态，地图标题固定为“今日事件分布”，不显示旧场景路线、点位或场景页签。全部 23 条事件及其状态、责任人和坐标均为模拟数据。

### REQ-MAP-RESOURCE-01 资源点详情与道路命中边界

城市尺度资源点与调度卡共用当前 MapLibre 画布，不创建第二张地图。点击医疗机构、消防救援站等资源时，详情卡锚定在该资源点上方，至少展示名称、类型、位置/地址、数据来源与获取时间；若叠加调度状态、车辆、能力或 ETA，必须另行标“模拟”。

公开静态 POI 的名称和坐标可来自 OSM 快照及可追溯的 OSM 对象链接；未提供结构化地址时诚实显示“公开快照未提供”，不得补造。资源 Marker 的点击优先级高于道路图层，内容中不得混入道路 way id。

城市总览、今日事件和资源调度中的普通地图点击不弹出道路详情或封路操作。道路继续作为空间背景；5·16 等处置链中明确依赖的封路/绕行控制仍保留在工作流详情态。

### REQ-DOMAIN-01 同级呈现

119、110、120、交通、重大布防使用同层级视觉组件呈现，**同级展示而不是筛选按钮**，不以隐藏次级菜单表达（D-02）。五项均须拥有可进入的模拟业务场景，而不是只有展示入口。

五项复用同一个事件工作流核心：模拟输入/事件建立 → 六块 Brief → A/B 方案 → 人工批准 → 任务包 → 模拟送达 → 条件调整后的重算与重新批准。每项通过独立 fixture 提供自身的事件类型、可编辑字段、资源、风险和任务文案。它们不得暗示真实 120 调度、真实重大布防引擎或真实跨部门联动。

**同级 ≠ 等深。** 视觉与入口同级是 D-02 的要求；做到哪一步由 REQ-DOMAIN-02 分档。

## 日常响应

### REQ-ROUTINE-01 两个模拟入口

两个入口都保留（21:05 会 03:31–03:52），但**两者都只承载「高层火情」一个场景**（21:05 会 04:40，工作量原因）。不做第二个日常场景。

入口 A 为“模拟事件流注入”：打开系统时预设时序自动弹出事件。叙事目的是"系统在实时监控这座城市"。

入口 B 为“工作人员手工输入”：从预验证模板预填，可编辑受限结构化字段，补充描述可自由填写。叙事目的是"这套系统可复用，你给模拟数据我们也能推演"。

两个入口必须汇聚到同一事件工作流，不得形成两套互相不一致的事件、批准或任务状态。入口、Signal 和生成事件均显示“模拟事件 / 未接真实源”。

### REQ-ROUTINE-02 事件建立

提交有效输入后，界面展示：地址标准化、事件 ID、关联建筑、周边资源、道路/天气关联和态势摘要生成的短过程；产出事件编号、标准地址/坐标、研判中状态、输入信号列表和接口/演示数据来源标签。

### REQ-BRIEF-01 六块 AI Brief

每块至少三条有效信息，所有条目有来源和确认状态，并以真实/模拟/估算/未知口径呈现：

1. 核心态势结论：当前事件、处置位置与本轮需要人工判断的重点；
2. 事件事实与证据：时间、地点、事件类型/等级、关键人员或建筑信息；
3. 风险研判与优先级：未知项造成的风险、P0/P1 优先级、核实责任人或渠道；
4. 态势趋势预测：只展示基于当前输入和显式假设的条件推演，不预测事故是否发生；
5. 周边资源与现实约束：建筑、周边资源、道路、天气及系统能力边界；
6. 关键信息缺口：缺口、当前默认假设、受影响方案/指标、重新研判触发条件。

补充描述只能作为线索或待核实信息，不能自动升级为已确认事实。

### REQ-PLAN-01 候选方案与人工门禁

至少生成 A/B 两个完整方案。每个方案须包含目标、触发依据、关键假设、资源组合、人员/车辆、路线/时间窗、部门行动顺序、风险与缺口、备选/降级条件、预计到场时间与影响范围。

人工可选择方案、修改人员/资源/负责人、增删任务、填写决策说明、批准，或否决并重新生成。未批准前不得生成有效任务包或送达。

### REQ-DELIVERY-01 任务、送达与受控重试

批准后产生两个输出：事件处置方案卡和负责人任务包。任务包必须引用当前批准版本。

前端状态链为：

```text
待生成 → 待发送 → 已送达 → 已签收 → 执行中 → 已完成 / 异常
```

本期状态均为模拟，界面明确显示接收人、角色/部门、发送时间、内容摘要、当前状态和模拟签收入口，并预留但不调用外呼/短信/系统任务接口。

受控重试只演示一次：先显示一次模拟异常；工作人员调整车辆数量、资源点或负责人后，系统重新计算 ETA 和覆盖风险摘要，旧批准立即失效；完成再次人工批准后才可进行一次重试。第二次重试不可用。

若某项调整不具备可计算的 ETA 影响，界面必须诚实展示“ETA 未变化/当前模型不适用”，只更新可解释的覆盖风险或任务影响，不能编造数值变化。

### REQ-REPLAN-01 不变量

以下任一变化均使旧批准、旧任务包和旧送达资格失效：车辆数量、资源点、负责人、封路或其他影响方案的关键条件。

```text
调整 → 重算完成 → 旧批准失效 → 人工重新批准 → 生成新版本任务包 → 才能送达/重试
```

禁止“修改后继续沿用旧批准”。

## 历史案例：5·16 与广州火车站

两个案例共用本节的全部规则。5·16 有完整三轨对比；广州火车站持刀伤人的公开度更低，见 REQ-HISTORY-03。

### REQ-HISTORY-01 公开事实与模拟隔离

先展示官方公开事实、公开时间锚点、已知数据和缺口。缺失的原处置路线、车辆编成、路口协同、签收和首车到场可使用“公众信息约束下的基线处置模拟”补足展示，但必须与公开事实和 CityOS 模拟方案分层呈现。基线模拟不得写成真实历史还原。

三条口径的固定命名为：

1. `5·16 公开事实与缺口`：只放有来源的时间、地点、事件、公开报道及明确未知项；
2. `公众信息约束下的基线处置模拟`：根据公开锚点构造的常规资源、路线、ETA、任务与反馈假设；
3. `CityOS 方案模拟`：在同一事件时点、同一公开地理快照和同一假设集下的替代方案。

只有两条模拟轨使用相同 `assumptionSetId`、路网快照和模型版本时，才显示“可直接比较”。公开锚点使用绝对时间，模拟轨使用 `T+` 相对时间，避免伪造历史到场时刻。

### REQ-HISTORY-02 推演、动态舞台与对比

历史侧复用六块 Brief、A/B 候选方案和人工批准门禁，但 CityOS 结果须明确为模拟。

批准后进入独立动态舞台，至少呈现：街区级建筑/道路、事件高亮、模拟车辆从资源点出发、选定路线推进、路况/封闭/绕行状态、关键路口节点、任务状态、时间线和模拟执行异常/到场阶段。

动态舞台结束后展示“公开事实”“公众信息约束下的基线处置模拟”与“CityOS 方案模拟”的三轨对比，包括公开时间锚点、ETA 估算、资源假设、提前任务、受阻点、额外成本、未解决风险和数据/推演边界。禁止使用“证明真实更优”等表述。

视觉舞台优先保证叙事、地图关系和状态变化可读。使用已经安装的 deck.gl `TripsLayer` 和 MapLibre 原生图层/镜头动画，不新增依赖。一个 `playhead` 必须同时驱动车辆位置、路线样式、镜头、任务状态和底部时间线；播放、暂停、重放和时间线拖动必须改变同一个 `playhead`。开启 reduced-motion 后改为离散阶段切换，不保留逐帧动画。

### REQ-HISTORY-03 广州火车站持刀伤人的公开度边界

该场景基于真实公开事件（D-20），因此适用与 5·16 相同的三轨口径与形状编码。但公开度显著更低，须额外遵守：

**可标为公开事实的只有**：日期、时刻、地点、伤亡数、"发现 → 鸣枪示警 → 击毙/抓获"这个粗粒度序列、现场封锁解除时刻。每一项都要附来源链接。

**必须走"公众信息约束下的基线处置模拟"的**：警力编成、到场路线、医院分流、指挥流程、任务签收回执——这些没有任何公开记录，一律标模拟。

**不得使用的**：涉案人员的身份、籍贯等信息。公开报道里有，但与调度处置叙事无关，产品内不出现。

伤亡数以已核验的一手/权威媒体通报为准，并标注"当日通报口径"；未核验的数字不进产品（U-11）。

### REQ-KNOWLEDGE-01 知识沉淀方向

21:05 会 05:19–05:37 拍板：做知识沉淀库，**换掉“案例库”这个名字**（名称待定，见 U-05）。这条推翻了 17:59 会 03:55“复盘这块就不要了，换 setting 壳”的说法。

对外口径已定：每次推演沉淀下来的数据在知识库保留，用于模型参数校准。

以演示优先实现可见的“知识沉淀草稿”：案例标题、已确认事实、未知项、CityOS 模拟方案摘要、数据来源、生成时间和当前演示版本。若未接后端，必须标“演示草稿 / 未写入知识库”，可提供复制摘要或打印/PDF，**不得伪造同步成功**——对外口径说的是"会保留"，界面不能因此显示"已入库"。

## 演示脚本约束

### REQ-DEMO-01 现场怎么演

来自 16:15 会（荆渤韬主持）。这些不是功能需求，是演示动作，比功能更硬——功能做到了但演不出来等于没做。

1. **日常响应必须当场手输**，不能像荔湾那样点一下直接出结果（16:15 会 07:08）。输入框必须真的可编辑，不能是走过场的假交互。
2. 手输内容**必须落在预设模板范围内**（16:15 会 06:15；17:59 会 06:32 再次强调）。
3. **评委不操作，我方操作**（16:15 会 07:20–07:23，康莹当场确认）。
4. 目标状态是让评委"觉得我们是随机输入的数据，并且能响应出方案"。
5. 主看板默认带异常汇总，不做"一切正常"的空态——16:15 会 05:55："城市治理安全这块不可能有正常状态，它肯定有实时的数据流和工作流在跑"。
6. 地图图层语言对齐高德/百度的道路交通表达。现有"点进去一个绿色的道、原本那个加粗加深"已被否决；天气那类"一个圆圈上去"的组件判定为"产品语言不对"（16:15 会 03:38–03:57、08:07）。
